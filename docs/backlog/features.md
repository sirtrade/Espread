# Большие фичи

> Порядок = приоритет: верхняя задача — самая важная. Формат и процесс — в
> `README.md` этой папки.

## F-17. Кнопка «Пропустить статью» с мини-анкетой причины
- **Приоритет:** P1 — владелец регулярно получает статьи, которые не хочет
  читать (повтор сюжета, неинтересная тема), а легального способа отказаться
  нет: активная сессия «прилипает» (`startReading` всегда возвращает её), и
  единственный обход — дочитать через силу или бросить приложение.
- **Проблема/мотивация:** Приложение периодически выдаёт одну и ту же новость
  из разных источников (пример владельца — сюжет про WhatsApp три раза), а
  иногда тема просто не интересна. Пропуск нужен как базовое право читателя,
  а анкета причины — как сигнал для будущего подбора тем (см. F-18, F-19).
- **Что сделать:**
  1. **API.** `POST /api/session/skip` (под `withUserLock("session:"+userId)`):
     принимает `{ reason?: "repeat" | "not_interested" | "too_hard" | "other",
     comment?: string }` (comment ≤ 200 символов, только при `other` — или при
     любой причине, согласовать с владельцем); фиксирует пропуск и удаляет
     активную сессию одним действием. Без активной сессии → 404. Причина
     опциональна: анкету можно закрыть, пропуск всё равно происходит.
  2. **Схема.** Drizzle-миграцией добавить в `articles` колонки
     `skipped_at` (integer, ms), `skip_reason` (text), `skip_comment` (text) —
     статья читается/пропускается максимум один раз, отдельная таблица не
     нужна. Существующие строки не трогать (default NULL).
  3. **Никаких кредитов.** Пропуск не пишет SRS/банк, не инкрементит
     `known_words`, не ставит `daily_activity.reading`, не увеличивает
     `user_stats.articlesRead`, не влияет на стрик. Пометки (`marks`) сессии
     отбрасываются. В историю чтения статья не попадает (там фильтр
     `readAt IS NOT NULL` — покрыть тестом). Тема пропущенной статьи ДОЛЖНА
     продолжать учитываться в `getRecentTopics` (ротация по `createdAt` — уже
     так, зафиксировать тестом).
  4. **UI (`webapp/src/screens/Reading.tsx`).** Кнопка «Пропустить» в хроме
     экрана (согласовать место: нижняя панель рядом с «Готово» или меню в
     шапке). Тап → bottom-sheet-анкета: «Почему пропускаешь?» с вариантами
     «Уже читал(а) об этом» / «Тема не интересна» / «Слишком сложно» /
     «Другое» + поле текста, и возможностью закрыть без ответа. После
     пропуска — предложение «Nueva lectura» (обычный `startReading`).
  5. **Лимиты.** Пропуск не возвращает потраченный `generate`; следующая
     статья подчиняется `DAILY_ARTICLE_LIMIT` как обычно (естественная защита
     от бесконечного перелистывания). При исчерпании лимита показывается
     существующая обработка 429.
  6. Показывать ли кнопку в состоянии `reviewed` (разбор уже оплачен LLM) —
     согласовать с владельцем; эскиз: скрывать после запуска разбора.
- **Критерии приёмки:**
  - На экране чтения есть кнопка пропуска; анкета показывает 4 варианта +
    кастомный текст и закрывается без выбора; все строки — i18n ru/en/es.
  - `POST /api/session/skip` удаляет сессию, пишет
    `skipped_at`/`skip_reason`/`skip_comment` на статью; повторный вызов → 404.
  - После пропуска ни одна из метрик прогресса не изменилась (тест уровня
    сервиса), статья не отображается в истории, её тема учитывается в ротации.
  - Пропуск + `startReading` выдают новую статью в рамках дневного лимита.
  - `npm run typecheck`, `npm test` проходят; миграция совместима с
    существующими строками; `docs/functionality-registry.md` обновлён
    (§5.4, §6.6, §17, §20, §22).
- **Детали/ссылки:** `server/src/api/routes/session.ts` (там уже есть
  неиспользуемый UI `DELETE /api/session` — пропуск делать отдельным
  эндпоинтом с записью причины, DELETE оставить как есть),
  `server/src/services/articleService.ts` (`startReading`),
  `server/src/db/schema.ts` (`articles`, `readingSessions`),
  `webapp/src/screens/Reading.tsx`, `webapp/src/api/client.ts`;
  реестр §5.4, §6.6, §15.

## F-18. Дедупликация сюжетов при поиске новости
- **Приоритет:** P1 — это корневая причина жалобы «одна и та же статья из
  разных источников»: даже с кнопкой пропуска (F-17) генератор продолжит
  находить тот же громкий сюжет.
- **Проблема/мотивация:** Ротация тем избегает лишь двух последних тем
  (`pickTopic`), а поисковый шаг (§6.2) ничего не знает о прошлых статьях:
  промпт просит «одну свежую новость по теме», и модель раз за разом приносит
  самый заметный сюжет недели, лишь меняя источник.
- **Что сделать:**
  1. Чистая функция сборки «списка избегания»: последние N заголовков статей
     пользователя (прочитанных и пропущенных; после F-17 пропущенные с
     причиной `repeat` — в первую очередь), окно и N — константами с
     обоснованием (эскиз: 15 статей / 14 дней; длинные заголовки обрезать).
  2. Передавать список в промпт `runSearchStep` явным запретом: «найди сюжет,
     который НЕ пересекается со следующими недавними историями: …». Свежая
     генерация и префетч идут через общий `generateFreshArticle` — покрываются
     оба пути автоматически.
  3. (Опционально, согласовать с владельцем) дешёвая пост-проверка: если
     заголовок/факты найденного сильно совпадают с недавним — один ретрай с
     усиленной инструкцией; можно отложить на отдельную итерацию, если
     промпт-запрета окажется достаточно.
- **Критерии приёмки:**
  - Промпт поиска содержит список недавних сюжетов пользователя; при пустой
    истории промпт не содержит пустого блока.
  - Функция сборки списка покрыта тестами (лимит N, окно по времени, обрезка
    заголовков, приоритет пропущенных-как-повтор при наличии F-17).
  - Дополнительных LLM-вызовов нет (кроме согласованного опционального
    ретрая); `npm run typecheck`, `npm test` проходят; реестр §6.1–6.2
    обновлён.
- **Детали/ссылки:** `server/src/llm/articleGeneration.ts` (`runSearchStep`),
  `server/src/services/articleService.ts` (`generateFreshArticle`),
  `server/src/db/repositories/articles.ts` (заголовки уже хранятся, нужна
  выборка последних N); реестр §6.1, §6.2. Не зависит от F-17 (работает уже
  по прочитанным статьям), но усиливается его данными.

## F-19. Учёт причин пропуска при выборе следующих тем
- **Приоритет:** P2 — полезная надстройка над F-17/F-18: превращает разовые
  пропуски в персонализацию подбора.
- **Проблема/мотивация:** Сигнал анкеты (F-17) должен менять поведение
  генератора, иначе пользователь будет пропускать одни и те же неинтересные
  темы вручную снова и снова.
- **Что сделать:**
  1. **Взвешенная ротация тем.** `pickTopic` расширить весами: тема с
     недавними пропусками `not_interested` выбирается реже (эскиз: вес
     `1 / (1 + количество таких пропусков за 30 дней)`), правило «избегать две
     последние темы» и fallback на полный список сохранить. Константы — с
     обоснованием в реестре.
  2. **Предложение убрать тему.** После K (эскиз: 3) пропусков одной темы с
     причиной `not_interested` — мягкая подсказка «Убрать тему X из
     интересов?» (форму — баннер на Home или в Settings — согласовать с
     владельцем). Никогда не удалять тему автоматически.
  3. **Причина `repeat`** — заголовок пропущенной статьи попадает в список
     избегания F-18 с наивысшим приоритетом (если F-18 уже сделан — просто
     зафиксировать тестом).
  4. **Кастомные комментарии (`other` + текст).** Эскиз: передавать последние
     M комментариев в промпт поиска как негативные предпочтения читателя.
     Спорно (свободный текст в промпте: качество сигнала, длина, prompt
     injection) — согласовать с владельцем, нужно ли это в первой итерации
     или достаточно смотреть комментарии руками в БД.
- **Критерии приёмки:**
  - `pickTopic` (или преемник) принимает статистику пропусков и покрыт
    тестами: понижение веса, сохранение avoid-правила, fallback при
    вырождении всех весов, отсутствие влияния пропусков с другими причинами.
  - Подсказка «убрать тему» не появляется до порога K и исчезает после
    решения пользователя; строки — i18n ru/en/es.
  - `npm run typecheck`, `npm test` проходят; реестр §6.1 и §22 обновлены.
- **Детали/ссылки:** `server/src/domain/topicRotation.ts`,
  `server/src/services/articleService.ts`, данные пропусков из F-17
  (`articles.skip_reason`), список избегания из F-18; реестр §6.1.
- **Зависимость:** F-17 (данные анкеты); синергия с F-18.

## F-16. Эксперимент по вплетению грамматических конструкций
- **Приоритет:** P3 — требует отдельного решения владельца перед реализацией.
- **Проблема/мотивация:** Встреча конструкции в естественном чтении полезна, но
  текущий строковый `termAppearsIn` не может подтвердить синтаксический шаблон,
  а принудительное вплетение рискует ухудшить текст.
- **Что сделать:** Спроектировать opt-in эксперимент: не более одной
  due-конструкции на статью, структурированное подтверждение из финального
  текста и независимый аудит естественности/CEFR-fit. Экспозиция не даёт
  SRS-кредит.
- **Критерии приёмки:** до кода утверждены дизайн и бюджет; контрольная группа
  не получает grammar target; неподтверждённый паттерн не считается встречей;
  качество статьи не ослабляется; стоимость учитывается отдельно.
- **Детали/ссылки:** `docs/grammar-track-design.md` §9–10;
  `server/src/llm/articleGeneration.ts`, `server/src/llm/articleQuality.ts`.
- **Зависимость:** F-12; отдельное утверждение владельца.
