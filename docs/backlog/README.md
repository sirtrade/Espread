# Реестр задач (backlog)

> Единственное место, где фиксируются все планируемые изменения приложения.
> Правило: **сначала задача попадает сюда, потом реализуется.** Ничего не
> реализуется «мимо» backlog'а — иначе теряется картина того, что сделано,
> а что нет.

## Структура

| Файл | Что лежит |
|---|---|
| `bugs.md` | Баги и расхождения с документацией (ID `B-*`) |
| `micro.md` | Микро-фиксы: мелкие улучшения на 1–2 часа работы (ID `M-*`) |
| `features.md` | Большие фичи (ID `F-*`) |
| `tech.md` | Техдолг и инфраструктура (ID `T-*`) |
| `archive.md` | Выполненные задачи (переносятся сюда целиком) |

Внутри каждого списка задачи упорядочены по приоритету: **верхняя — самая
важная**. Приоритеты: `P0` (блокер) → `P1` (важно) → `P2` (полезно) → `P3`
(идея, требует обсуждения).

## Формат задачи

```markdown
## <ID>. <Короткое название>
- **Приоритет:** P0 | P1 | P2 | P3
- **Проблема/мотивация:** зачем это нужно, что болит сейчас.
- **Что сделать:** конкретные шаги или эскиз решения.
- **Критерии приёмки:** проверяемые условия «сделано».
- **Детали/ссылки:** файлы, разделы реестра функционала, этапы роадмапа.
```

ID выдаются последовательно и **никогда не переиспользуются** (счётчик
продолжает расти даже после архивации — так ссылки на задачи остаются
однозначными).

## Процесс

### Добавление задачи
Когда владелец хочет что-то добавить/изменить в приложении, агент **сначала**
записывает задачу в подходящий список в стандартном формате (уточнив
приоритет и место в списке), и только потом — если владелец просит —
приступает к реализации.

### Взятие задачи агентом-исполнителем
1. Агент берёт **ровно одну** задачу: указанную владельцем по ID, либо (если
   ID не назван) верхнюю из первого непустого списка в порядке
   `bugs → micro → features → tech`.
2. Перед реализацией читает `docs/functionality-registry.md` (что уже есть) и
   раздел «Детали/ссылки» задачи.
3. Реализует только эту задачу. Заметил попутный баг — **не чинит**, а
   добавляет карточку в `bugs.md`.

### Завершение задачи (обязательная часть Definition of Done)
1. Выполнены критерии приёмки из карточки.
2. `npm run typecheck` и `npm test` в `server/` проходят; на новую доменную
   логику написаны тесты; новые строки UI — через i18n (ru/en/es).
3. Обновлён `docs/functionality-registry.md` (если менялся функционал) и
   `docs/retention-roadmap.md` (если задача закрывает его этап).
4. Карточка задачи **перенесена в `archive.md`** (с датой, веткой/PR) и
   **удалена** из исходного списка — в том же PR, что и код.

## Промт для добавления задач в backlog (копировать как есть)

```text
Прочитай docs/backlog/README.md (структура списков и формат карточек) и
docs/functionality-registry.md (что в приложении уже реализовано).

Я хочу добавить в backlog следующее:

<опиши идею, фичу или баг своими словами>

Твоя задача — только завести карточку, ничего не реализовывать:
1. Проверь, нет ли уже такой или пересекающейся карточки в списках backlog'а
   и в archive.md, и не реализовано ли это уже (по реестру функционала).
   Если есть пересечение — скажи об этом и предложи: дополнить существующую
   карточку или создать новую.
2. Выбери список (bugs / micro / features / tech) и присвой следующий
   свободный ID этого списка (ID не переиспользуются, смотри и архив).
3. Напиши карточку в стандартном формате: приоритет (предложи и обоснуй),
   проблема/мотивация, что сделать (эскиз решения; спорные места пометь как
   «согласовать с владельцем»), проверяемые критерии приёмки, ссылки на файлы
   и разделы реестра функционала.
4. Вставь карточку в список на место, соответствующее приоритету
   (верх = важнее).
5. Если моё описание неоднозначно — сначала задай уточняющие вопросы, потом
   пиши карточку.
6. Закоммить и запушь изменение.
```

## Промт для агента-исполнителя (копировать как есть)

```text
Прочитай docs/backlog/README.md и следуй его процессу.

Возьми задачу <ID> (если ID не указан — верхнюю задачу из первого непустого
списка в порядке bugs.md → micro.md → features.md → tech.md). Реализуй ровно
одну эту задачу, ничего кроме неё.

Обязательно:
- сначала прочитай docs/functionality-registry.md и материалы из раздела
  «Детали/ссылки» карточки;
- выполни все критерии приёмки из карточки;
- тесты на новую доменную логику; npm run typecheck и npm test в server/
  должны проходить;
- все новые строки UI — через i18n (ключи для ru/en/es), без хардкода;
- изменения схемы БД — только миграцией drizzle, без ломки существующих строк;
- обнови docs/functionality-registry.md в том же PR (это часть Definition of
  Done реестра);
- перенеси карточку задачи в docs/backlog/archive.md, добавив дату и
  ветку/PR, и удали её из исходного списка — в том же PR.

Если по ходу нашёл посторонний баг или идею — не реализуй, а добавь карточкой
в подходящий список backlog'а.
```
