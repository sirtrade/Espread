## F-8. Адаптация уровня CEFR по плотности пометок
- **Выполнено:** 2026-07-15, ветка `feat/f-8-level-suggestion`
- **Приоритет:** P2
- **Проблема/мотивация:** Уровень выбирался вручную и не использовал готовый
  сигнал понимания — долю реально помеченных слов в завершённых статьях.
- **Что сделано:** Чистый домен считает lexical-token density по последним пяти
  чтениям, дедуплицируя позиционные пересечения и нормализованные legacy-марки.
  Только пять значений строго ниже 2% предлагают соседний уровень вверх; только
  пять строго выше 8% — вниз. A2/C2 ограничивают края. Баннер на Home и сразу
  после completion предлагает сменить уровень или оставить текущий; автосмены
  нет. Показ/отказ сохраняются атомарным endpoint и дают cooldown 14 локальных
  календарных дней. Фактическая смена уровня и reset progress чистят stale
  metadata. `GET /stats` остаётся read-only, а completion сразу возвращает
  вычисленное предложение.
- **Критерии приёмки:** Покрыты все уровни включая C2, строгие пороги, окно <5,
  mixed window, overlap/dedupe/cap/zero, timezone cooldown, dismissal, API,
  immediate completion и reset. UI и строки локализованы ru/en/es.
- **Детали/ссылки:** `server/src/domain/levelSuggestion.ts`,
  `server/src/services/levelSuggestionService.ts`,

## F-7. Качество дистракторов
- **Выполнено:** 2026-07-15, ветка `feat/f-7-distractors`
- **Приоритет:** P2
- **Проблема/мотивация:** Статический fallback из 10 слов быстро выучивается
  как «всегда неправильные» — карточка решается исключением без знания слова.
- **Что сделано:** Основной review и legacy enrichment генерируют 5–8
  семантически правдоподобных same-POS испанских дистракторов близкой темы,
  длины и регистра, исключая синонимы и формы ответа. Zod сохраняет
  совместимость с массивами из трёх элементов (3–8). Серверный fallback и
  клиентское зеркало расширены до 30 noun/verb/adj; в каждую сборку попадает
  случайная подвыборка с инъецируемым `random`. Сохранён приоритет
  stored → bank → fallback, части речи и фразы не смешиваются, у phrases нет
  fallback, MC по-прежнему содержит четыре варианта.
- **Критерии приёмки:** Покрыты границы схемы, качество обоих промптов,
  детерминированная вариативность fallback, приоритет источников и фразы;
  F-5 anti-leak и F-6 context rotation остаются под существующими тестами.
- **Детали/ссылки:** `docs/retention-roadmap.md` этап 9,
  `server/src/domain/practice.ts`, `webapp/src/lib/cards.ts`,
  `server/src/llm/review.ts`, `server/src/llm/enrichBank.ts`.

## F-6. Ротация контекстов карточки
- **Выполнено:** 2026-07-15, ветка `feat/f-6-context-rotation`
- **Приоритет:** P2
- **Проблема/мотивация:** Cloze всегда строился из одного и того же
  `firstContext` — пользователь запоминал предложение, а не слово; знание не
  переносилось на новые контексты.
- **Что сделано:** Добавлена nullable/default-compatible JSON-колонка `contexts`

  Práctica и бот выбирают контекст до сборки карточки с инъецируемым `random`;
  cross-card anti-leak работает по выбранному предложению. Typed-очередь не
  раскрывает ответ до grading, а непрозрачный `addedAt` сохраняет выбранный
  корректирующий feedback в webapp и pending-викторине бота. Легаси-поля
  `firstContext`/`contextTranslation`/`surfaceForm` сохранены как fallback.
- **Критерии приёмки:** Покрыты malformed/legacy JSON, dedupe/cap,
  детерминированный выбор, накопление при completion, разные prompts и
  anti-leak выбранного контекста; сервер и webapp типизируются и тестируются.
- **Детали/ссылки:** `docs/retention-roadmap.md` этап 8,

## F-3. Реестр известных слов и оценка словарного запаса
- **Выполнено:** 2026-07-15, ветка `feat/f-3-known-words`
- **Приоритет:** P1
- **Проблема/мотивация:** Хочется видеть персональный словарный запас
  пользователя, а не только слова «в изучении». Банк отвечает на вопрос «что
  я учу», реестр известных слов — на вопрос «что я уже знаю». На его основе
  можно оценивать объём словарного запаса и его рост. Объём БД не критичен
  (подтверждено владельцем: пользователей немного, единицы гигабайт — ок).
- **Что сделать (эскиз; детальный дизайн — за исполнителем, спорные места
  согласовать с владельцем до реализации):**
  1. Таблица `known_words`: `user_id`, `lemma`, unique `(user_id, lemma)`,
     `source` (`learned` — прошёл SRS-лестницу; `reading` — многократно
     прочитан без пометки; `manual` — отмечен вручную), `encounters`
     (счётчик встреч в статьях), `first_seen_at`, `last_seen_at`,
     `known_since` (когда признано известным, null пока копится счётчик).
  2. Наполнение: (а) graduation в `learned` → сразу запись с
     `source=learned`; (б) при завершении чтения — все леммы статьи, которые
     пользователь НЕ пометил и которых нет в банке, инкрементят `encounters`;
     при `encounters >= N` (стартовый порог — 3, вынести в константу) слово
     признаётся известным с `source=reading`. Для получения лемм статьи:
     самый дешёвый вариант — просить их у LLM на шаге написания статьи
     (`runWriteStep` уже возвращает JSON — добавить поле `lemmas`); оценить
     стоимость, альтернатива — локальная лемматизация/стемминг
     (`termAppearsIn` уже есть как основа). Выбор согласовать с владельцем.
  3. Экран «Словарный запас» (вход с Home): общий размер реестра, разбивка
     по источникам, динамика по неделям (слова/неделя).
  4. Оценка объёма: сопоставить известные леммы с частотным списком испанского
     (например, топ-5000) и показывать покрытие по диапазонам частотности
     («знаешь ~X из первой тысячи, ~Y из второй…») с экстраполяцией общего
     запаса.
- **Критерии приёмки:** `learned`-слова автоматически появляются в реестре;
  непомеченные слова прочитанных статей накапливают встречи и после порога
  попадают в реестр; экран показывает размер реестра, динамику и оценку
  покрытия частотного списка; сброс прогресса (`DELETE /me/progress`) чистит
  и реестр; всё локализовано; `docs/functionality-registry.md` дополнен новым
  разделом.
- **Детали/ссылки:** `server/src/domain/weaving.ts` (`termAppearsIn`),
  `server/src/llm/articleGeneration.ts`, `server/src/db/schema.ts`,
  `docs/functionality-registry.md` §8, §20. Учитывать F-2: после понижения
  веса чтения `learned` становится честным сигналом — реестр от этого только

## F-10. Независимый контроль качества сгенерированных статей
- **Выполнено:** 2026-07-15, ветка `feat/f-10-article-quality` (код
  `f731457`)
- **Приоритет:** P1
- **Проблема/мотивация:** Единственный writer-вызов мог сохранить статью с
  неподходящим CEFR, неестественными коллокациями, декоративно сложной лексикой
  или некорректной длиной. Самооценка тем же автором усиливала bias, а сбой
  дополнительной проверки не должен был ломать чтение.
- **Что сделано:** CEFR-профили и общие правила естественности вынесены в
  `server/src/llm/articleRubric.ts`. После написания статья проходит локальные
  детерминированные проверки длины и абзацев, независимый структурированный
  LLM-аудит и при необходимости до двух минимальных rewrite-попыток. Решение о
  rewrite принимает сервер по hard-fail, major-проблемам и порогу оценок, а не
  по boolean модели. При сбое сохраняется лучшая доступная версия. Вызовы
  `audit`/`rewrite` учитываются в стоимости, но не расходуют дневной лимит
  генераций. Реестр функционала §6.3–6.4 и §22 обновлён.
- **Критерии приёмки:** Чистая статья сохраняется без rewrite; объективный
  hard-fail, major-проблема или оценка ниже 4 запускают rewrite; выполняется не
  более двух rewrite; при ошибке LLM генерация деградирует к лучшему тексту, а
  не отвечает 500; схемы отклоняют некорректный verdict; CEFR-рубрики и
  локальные проверки покрыты тестами. `npm run typecheck` и `npm test` в
  `server/` проходят (223 теста).
- **Детали/ссылки:** `server/src/domain/articleQuality.ts`,
  `server/src/llm/articleQuality.ts`, `server/src/llm/articleRubric.ts`,
  `server/src/llm/articleGeneration.ts`, `server/src/llm/schemas.ts`,
  `server/tests/articleQualityChecks.test.ts`,
  `server/tests/articleQualityPipeline.test.ts`,
  `server/tests/articleQualitySchema.test.ts`,
  `server/tests/articleRubric.test.ts`, `docs/functionality-registry.md` §6.

## B-2. Анти-фарм SRS считается по UTC-суткам, а не по локальным
- **Выполнено:** 2026-07-15, ветка `claude/backlog-task-impl-z0hm94`
- **Приоритет:** P2
- **Проблема/мотивация:** `creditAllowedToday`/`isSameUtcDay`
  (`server/src/domain/srs.ts`) сравнивали календарные сутки в UTC. Для
  пользователя в UTC+3 два «кредита» (подъёма по лестнице) были возможны в одни
  локальные сутки: например, в 02:00 и в 23:00 по местному времени.
- **Что сделано:** Добавлен хелпер `localDayKey(ms, timeZone)` в
  `server/src/lib/timezone.ts` (ключ дня «YYYY-MM-DD» по таймзоне, безопасный
  откат на UTC при неизвестной зоне). `isSameUtcDay` заменён на
  `isSameLocalDay(a, b, timeZone)`, `creditAllowedToday` теперь принимает
  `timeZone`. Таймзона пользователя (`user.timezone`) прокинута в
  `applyPracticeAnswer` (Práctica через `POST /practice/answer`, бот-викторина)
  и `applyReviewToBank` (завершение чтения). Известное ограничение снято из
  `docs/functionality-registry.md` §8.2 и §24; статус этапа 10.1 в роадмапе
  обновлён.
- **Критерии приёмки:** Два успеха в одни локальные сутки дают один подъём;
  тесты с таймзонами UTC+3 (`Europe/Moscow`) и UTC−8 (`America/Los_Angeles`) —
  доменные (`server/tests/srs.test.ts`) и интеграционный через
  `applyPracticeAnswer` (`server/tests/integration.practiceAnswer.test.ts`);
  известное ограничение убрано из реестра функционала §8.2 и §24.
  `npm run typecheck` и `npm test` в `server/` проходят (165 тестов).
- **Детали/ссылки:** `docs/retention-roadmap.md` этап 10.1,
