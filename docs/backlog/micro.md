## M-3. Добавить уровень CEFR C2
- **Приоритет:** P2
- **Проблема/мотивация:** Приложение поддерживает только уровни A2/B1/B2/C1
  (сетка в онбординге и настройках, частотные потолки, enum в схеме). Верхняя
  ступень CEFR — C2 (владение, близкое к носителю) — отсутствует, поэтому
  продвинутые читатели упираются в потолок C1 (5000 самых частотных слов) и
  получают статьи проще, чем им нужно. Добавить C2 как ещё одну опцию уровня.
- **Что сделать (эскиз):**
  1. Расширить тип уровня и списки во всех точках: `Level` в
     `webapp/src/api/types.ts`, массивы `LEVELS` в `Onboarding.tsx` и
     `Settings.tsx`, тип в `server/src/llm/articleGeneration.ts` и
     `server/src/db/repositories/users.ts`, enum в `server/src/db/schema.ts`,
     Zod-схема `level` в `server/src/api/validation.ts`.
  2. Добавить частотный потолок C2 в `LEVEL_FREQ_CAP`
     (`server/src/llm/articleGeneration.ts`) и синхронно обновить тест
     `server/tests/reviewSchema.test.ts` (он ассертит точный объём объекта).
     **Значение потолка C2 — согласовать с владельцем**: предложение — ~8000
     (шаг относительно C1=5000). Отдельно **согласовать с владельцем**, уместна
     ли вообще модель «использовать почти исключительно N самых частотных слов»
     для near-native уровня, или для C2 инструкцию промпта стоит смягчить
     (журнальный/литературный регистр без жёсткого потолка).
  3. **Миграция БД, скорее всего, не нужна**: колонка `users.level` в схеме —
     это `text DEFAULT 'A2' NOT NULL` без CHECK-констрейнта (см.
     `server/drizzle/0000_*.sql`), enum действует только на уровне TypeScript,
     поэтому существующая БД уже примет значение `"C2"`. **Согласовать с
     владельцем**, добавлять ли всё же no-op-миграцию/CHECK для строгости, или
     ограничиться правкой `schema.ts`.
  4. Дефолт уровня остаётся `A2` (менять не нужно). Отдельные i18n-строки для
     кода уровня не требуются — метки уровней («A2», «C2» …) выводятся как есть,
     без пер-уровневых ключей словаря.
- **Критерии приёмки:**
  - `C2` доступен как опция в онбординге и в настройках; выбор сохраняется в
    профиле (`PATCH /api/me { level: "C2" }` проходит валидацию, значение
    персистит и возвращается в `GET /api/me`).
  - Генерация статьи для C2 использует потолок C2 из `LEVEL_FREQ_CAP`
    (`frequencyInstruction("C2")` не падает и подставляет согласованное
    значение); обновлённый `server/tests/reviewSchema.test.ts` зелёный.
  - `npm run typecheck` и `npm test` в `server/` проходят; webapp собирается и
    типизируется (исчерпывающие `switch`/`Record` по уровню, если есть, не
    ломаются на новом варианте).
  - `docs/functionality-registry.md` обновлён: §4 (сетка уровней), §6.3 и §22
    (частотные потолки), §14 (настройки уровня), §17/§20 (валидация и enum
    `users.level`).
- **Детали/ссылки:** `webapp/src/api/types.ts` (`Level`),
  `webapp/src/screens/Onboarding.tsx` (`LEVELS`),
  `webapp/src/screens/Settings.tsx` (`LEVELS`),
  `server/src/llm/articleGeneration.ts` (`LEVEL_FREQ_CAP`,
  `frequencyInstruction`), `server/src/api/validation.ts`,
  `server/src/db/schema.ts`, `server/src/db/repositories/users.ts`,
  `server/tests/reviewSchema.test.ts`, `docs/functionality-registry.md`
  §4, §6.3, §14, §17, §20, §22. Связано с F-8 (адаптация уровня по плотности
  пометок): после добавления C2 «повышение уровня» в F-8 должно доходить до C2
  как верхнего потолка.
