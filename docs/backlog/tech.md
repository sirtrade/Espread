# Техдолг и инфраструктура

> Порядок = приоритет: верхняя задача — самая важная. Формат и процесс — в
> `README.md` этой папки.

## T-1. Проверить Docker-сборку и сквозной прогон в реальном Telegram
- **Приоритет:** P1
- **Проблема/мотивация:** По собственному признанию README: Docker-образ ни
  разу не собирался, а полный пользовательский путь (онбординг → чтение →
  разбор → тренировка) проверялся только через REST-вызовы и тесты с
  замоканным LLM. До первого деплоя это главный риск: всё может быть «зелёным»
  и не работать в реальном клиенте.
- **Что сделать:**
  1. `docker compose up -d --build` — убедиться, что образ собирается,
     миграции применяются, `GET /health` отвечает, статика webapp отдаётся.
  2. Развернуть на публичном HTTPS-URL (или через ngrok), настроить бота у
     BotFather, пройти весь путь в реальном Telegram-клиенте: онбординг,
     чтение с пометками (тап, расширение в фразу, лонг-пресс предложения),
     разбор, quiz, práctica, банк, настройки, история, ежедневная доставка и
     бот-викторина.
  3. Найденные проблемы — карточками в `bugs.md` (не чинить в рамках этой
     задачи, если фикс не тривиален).
  4. Убрать соответствующие пункты из «Известных ограничений» README и
     реестра функционала (§24).
- **Критерии приёмки:** Прогон выполнен и задокументирован (краткий отчёт:
  что проверено, что найдено); ограничения из README/реестра сняты или
  заменены найденными багами в backlog'е.
- **Примечание:** Нужны реальные секреты (BOT_TOKEN, ANTHROPIC_API_KEY) и
  публичный URL — задача выполняется совместно с владельцем.
- **Детали/ссылки:** `README.md` «Известные ограничения», `Dockerfile`,
  `docker-compose.yml`, `start.sh`.

## T-2. Журнал ответов практики (фундамент для адаптивного планировщика)
- **Приоритет:** P2
- **Проблема/мотивация:** Фиксированная SRS-лестница одинакова для всех слов
  и пользователей. Современные планировщики (FSRS, Duolingo HLR) оценивают
  прочность следа индивидуально, но для этого нужна история ответов, которая
  сейчас не сохраняется — данные теряются безвозвратно с каждым днём.
- **Что сделать:** По этапу 10.3 + 10.5 роадмапа: таблица `practice_answers`
  (`user_id`, `item_id`, `ts`, `card_type`, `correct`, `used_hint`,
  `latency_ms`, `srs_stage_before/after`), запись из `applyPracticeAnswer`;
  замер latency на клиенте (время от показа карточки до ответа). Пока только
  копить данные — **сам FSRS не начинать без явного запроса владельца**.
- **Критерии приёмки:** Каждый ответ (webapp и бот) пишет строку журнала;
  latency приходит с клиента (для бота — null); ретраи внутри сессии в журнал
  не попадают (они не уходят на сервер); миграция без ломки существующих
  строк; реестр функционала дополнен (§20).
- **Детали/ссылки:** `docs/retention-roadmap.md` этап 10.3, 10.5,
  `docs/retention-audit.md` §10, `server/src/db/repositories/bank.ts`
  (`applyPracticeAnswer`).
