# Роадмап: закрытие пробелов в закреплении знаний

> **С 2026-07-13 очередь работ ведётся в `docs/backlog/`** — невыполненные
> этапы заведены там карточками (этап 5 → F-1, этап 6 → F-2, этап 7 → F-5,
> этап 8 → F-6, этап 9 → F-7, этап 10 → B-2 / M-1 / M-2 / T-2). Этот файл
> остаётся детальной спецификацией этапов: карточки backlog'а ссылаются сюда.

Источник: `docs/retention-audit.md` (аудит от 2026-07-12). Каждый этап — это
самостоятельная, независимо мерджимая единица работы для одного агента.
Внутри этапа задачи упорядочены по зависимости; между этапами зависимостей
нет, кроме явно указанных.

Общие правила для всех задач:

- Домены чистые: логика SRS/карточек живёт в `server/src/domain/*` (без
  I/O) и покрывается юнит-тестами в `server/tests/` (vitest,
  `npm test` в `server/`). Клиентские зеркала — `webapp/src/lib/srs.ts`,
  `webapp/src/lib/cards.ts` — держать синхронными с серверными.
- Все новые строки UI — через i18n (`webapp/src/lib/i18n.ts`, ключи для
  ru/en/es), не хардкодить русский.
- Изменения схемы БД — миграцией (drizzle, `server/drizzle/`), без ломки
  существующих строк: новые колонки nullable/с дефолтом.
- Не менять контракт `POST /practice/answer` ломающим образом: бот
  (`server/src/bot/quiz.ts`) и два экрана webapp используют один и тот же
  путь `applyPracticeAnswer`.

## Этап 1. Прерываемость сессии (UX-блокер)

**Проблема (аудит §6):** из `QuizSession` нет выхода; единственная кнопка —
«Далее». При этом каждый ответ уже сохраняется на сервер по одному, выход
безопасен.

**Задачи:**

1. В `webapp/src/components/QuizSession.tsx` добавить выход из сессии на
   каждом шаге (кнопка/крестик в шапке). Выход показывает существующий
   summary-экран, посчитанный по уже отвеченным карточкам (`answers`), с
   корректным `total = answers.length`, а не `cards.length`.
2. Подключить Telegram BackButton: в `webapp/src/telegram/telegram.ts`
   добавить обёртки `showBackButton(onClick)` / `hideBackButton()` над
   `window.Telegram.WebApp.BackButton`; в quiz/practice BackButton = тот же
   выход в summary; на Home — скрыт. Остальные экраны (Bank, History,
   Settings, Review) могут подключить его отдельной задачей.
3. Неотвеченные карточки просто не трогаем: слова остаются due, Práctica
   подхватит их в следующий раз. Ничего дописывать на сервер не нужно.

**Критерии приёмки:** можно выйти после любой карточки; summary показывает
только отвеченные; уже отправленные ответы сохранены (проверить по
`/practice/queue` — отвеченные слова исчезли из due); BackButton работает и
не остаётся видимым на Home.

## Этап 2. Восстановление усилия извлечения (retrieval effort)

**Проблема (аудит §2):** перевод предложения показывается ДО ответа
(`QuizSession.tsx`, блок `card.contextTranslation`) и фактически выдаёт ответ.

**Задачи:**

1. Спрятать `contextTranslation` за кнопку «Показать перевод» (состояние
   per-card, сбрасывается в `next()`); после ответа перевод показывается
   всегда (обратная связь — не трогать).
2. Прокинуть факт использования подсказки: `onAnswer(card, correct,
   {usedHint})` → `POST /practice/answer` с опциональным `usedHint: boolean`
   (расширить `practiceAnswerSchema` в `server/src/api/validation.ts`).
3. В `applyPracticeAnswer` (`server/src/db/repositories/bank.ts`):
   правильный ответ с подсказкой не даёт кредита (ступень и `nextDueAt` не
   меняются, слово остаётся due сегодня позже), неправильный — как обычно.
   Уточнить jsdoc функции.
4. Тесты: `server/tests/srs.test.ts` / `bank.test.ts` — кейс
   «correct + usedHint → без advance».

**Критерии приёмки:** в cloze до ответа перевода не видно; ответ с
подсказкой не двигает ступень (виден по ответу API `advanced: false`).

## Этап 3. Повтор ошибок внутри сессии

**Проблема (аудит §5):** ошибся → увидел ответ → карточка ушла до следующего
дня. После ошибки нужен успешный retrieval.

**Задачи:**

1. В `QuizSession.tsx`: при неправильном ответе ставить копию карточки в
   конец очереди (пометка `isRetry`). Повторять, пока не отвечена верно;
   ограничить двумя повторами на карточку, чтобы сессия гарантированно
   заканчивалась.
2. Retry-попытки НЕ отправляются на сервер (`onAnswer` не вызывается):
   SRS-исход слова определяет только первая попытка. Иначе повторный
   правильный ответ через минуту поднимет слово с 0 на 1 и сломает смысл
   `PRACTICE_RETRY_MS`.
3. Summary: слово с ошибкой показывать один раз (в списке «сброшено»),
   независимо от числа повторов; счётчик correct/total — по первым попыткам.
4. Перемешивание: retry не должен появляться немедленно следующим, если в
   очереди есть ≥2 других карточек (вставлять с отступом).

**Критерии приёмки:** ошибочная карточка возвращается позже в той же сессии;
на сервер уходит один ответ на слово; сессия не может зациклиться.

## Этап 4. Мягкий откат вместо полного сброса

**Проблема (аудит §3):** одна ошибка сбрасывает слово на ступень 0 — слово с
30-дневного интервала проходит всю лестницу заново.

**Задачи:**

1. `server/src/domain/srs.ts`: добавить `lapseSrs(currentStage, now,
   delayMs)` → `srsStage = max(0, currentStage - 2)`, `nextDueAt = now +
   delayMs`. Константу отката (`LAPSE_STAGE_DROP = 2`) — экспортировать.
2. Заменить использование `resetSrs` на `lapseSrs` в двух местах:
   - `applyPracticeAnswer` (`db/repositories/bank.ts`) — неправильный ответ;
   - `applyReviewToBank` (`domain/bank.ts`) — слово перемечено при чтении.
   `resetSrs` оставить только для ручной смены статуса
   (`setBankItemStatus`), где полный рестарт осмыслен.
3. Зеркало в `webapp/src/lib/srs.ts` — если там появится расчёт; summary-
   тексты (`quizSession.streakReset` и родня в i18n) переформулировать:
   не «прогресс сброшен», а «повторим раньше».
4. Тесты: лестница после ошибки со ступеней 0/1/5/7; ошибка на 0 остаётся 0.

**Критерии приёмки:** ошибка на ступени 5 даёт ступень 3 и короткий retry;
поведение задокументировано в jsdoc `srs.ts` (заголовочный комментарий файла
сейчас описывает полный сброс — обновить).

## Этап 5. Продуктивное воспроизведение (typed recall) в webapp

**Проблема (аудит §1):** в mini-app только выбор из 4 вариантов. Домен
typed-recall уже написан (`server/src/domain/typedQuiz.ts`: `buildTypedQuizCard`,
`gradeTypedAnswer`) и используется только ботом.

**Задачи:**

1. Сервер, `GET /practice/queue` (`server/src/api/routes/practice.ts`): для
   items со `srsStage >= TYPED_QUIZ_MIN_STAGE` строить карточку типа
   `"typed"` через `buildTypedQuizCard` (fallback на MC, если карточка не
   строится). Расширить `PracticeCard.type` до `"cloze" | "recall" | "typed"`;
   для typed отдавать `prompt` (перевод), `contextHint`, БЕЗ `accepted` — 
   ответ грейдится на сервере.
2. Грейдинг: расширить `POST /practice/answer` полем `typedAnswer?: string`.
   Если пришёл `typedAnswer` — сервер сам вычисляет `correct` через
   `gradeTypedAnswer` (accepted-формы берёт из item), возвращает `verdict`
   (`exact | spelling | wrong`) и правильный ответ. Поле `correct` в этом
   случае игнорировать (клиенту не доверяем).
3. Клиент: в `SessionCard` добавить тип `typed`; в `QuizSession.tsx` для
   typed-карточек рендерить текстовое поле + кнопку «Ответить», после
   ответа — вердикт («верно», «верно, но пишется …», «неверно») с показом
   правильной формы, перевода и контекста, как у MC.
4. Post-reading Quiz не трогать: слова там на ступени 0, MC уместен.
5. Тесты: queue отдаёт typed для stage≥2; answer с `typedAnswer` грейдится
   сервером; опечатка/акцент → correct со `spelling`.

**Критерии приёмки:** слово со ступени 2+ в Práctica требует ввода с
клавиатуры; MC остаётся для ступеней 0–1; бот продолжает работать без
изменений.

**Зависимость:** лучше делать после этапа 3 (retry-механика должна уметь
повторять и typed-карточки).

## Этап 6. Понизить вес пассивного чтения

**Проблема (аудит §4):** «чистая экспозиция» в статье двигает SRS наравне с
ответом в тесте и может довести слово до «learned» без единого retrieval.

**Задачи:**

1. В `server/src/domain/srs.ts` добавить `READING_CREDIT_MAX_STAGE = 2`.
2. В `applyReviewToBank` (`domain/bank.ts`): чистая экспозиция даёт advance
   только при `srsStage <= READING_CREDIT_MAX_STAGE`; выше — обновляет
   `exposures`, но не ступень и не `nextDueAt` (слово остаётся в ротации
   weaving по прежнему расписанию). Чтение никогда не graduate'ит: ветку
   `graduatesOnSuccess` из reading-пути убрать.
3. Graduation оставить только в `applyPracticeAnswer`. Опционально
   (согласовать с владельцем перед реализацией): требовать, чтобы
   выпускной успех был именно typed-ответом (после этапа 5 у
   `applyPracticeAnswer` появляется знание о типе ответа).
4. Обновить копирайт Review-экрана: `review.wovenHintSrs` и логику меток в
   `webapp/src/screens/Review.tsx` (там сейчас предсказывается «mastered»
   при `srsStage >= SRS_MAX_STAGE` от чтения — станет неверным).
5. Тесты: экспозиция на ступени 3+ не двигает расписание; слово на верхней
   ступени не graduate'ится чтением.

**Критерии приёмки:** довести слово до «learned» можно только ответами в
практике/боте; чтение помогает только на нижних ступенях.

**Статус:** готово (ветка `claude/backlog-task-impl-h129y8`, F-2). Добавлена
`READING_CREDIT_MAX_STAGE = 2` (`domain/srs.ts`); чистая экспозиция в
`applyReviewToBank` двигает ступень только при `srsStage <= 2` и никогда не
graduate'ит; graduation остался только в `applyPracticeAnswer`. Опциональный
пункт 3 (требовать typed-ответ для graduation) не реализован — помечен
«согласовать с владельцем» и в объём F-2 не входил. Копирайт Review-экрана
обновлён (`review.wovenHintSrs`, новый ключ `review.wovenPractice`).

## Этап 7. Interleaving и защита от утечек между карточками

**Проблема (аудит §7–8):** слова из одной статьи идут блоком (сортировка
`nextDueAt ASC`), делят контекст, и prompt одной карточки может содержать
ответ другой.

**Задачи:**

1. `getDueForPractice` (`db/repositories/bank.ts`): выбирать кандидатов с
   запасом (например `limit * 3` по `nextDueAt ASC`), затем в route
   перемешивать и брать `limit`. Просроченность сохраняет приоритет на
   уровне дня, порядок внутри выборки — случайный.
2. Анти-утечка в `GET /practice/queue` после сборки карточек: если
   `prompt`/`context` карточки A содержит `answer`/`lemma` карточки B той же
   выдачи (case-insensitive, по границам слов) — заменить контекстную
   утечку заглушкой `_____` или отбросить одну из карточек (предпочтительно
   ту, у которой есть альтернативный вариант recall/cloze).
3. То же правило в клиентском `buildQuizCards` (`webapp/src/lib/cards.ts`)
   для post-reading quiz — там все слова из одной статьи, риск максимален.
4. Тесты на чистую функцию анти-утечки (вынести в `domain/practice.ts`).

**Критерии приёмки:** в одной выдаче нет карточки, чей видимый текст содержит
ответ другой; слова одной статьи не идут сплошным блоком.

**Статус:** готово (ветка `feat/f-5-interleaving`, F-5). Репозиторий выбирает
`limit * PRACTICE_CANDIDATE_MULTIPLIER` (`3`) due-кандидатов, route перемешивает
их до сборки и после чистой cross-card проверки возвращает не больше `limit`.
Prompt-конфликты отбрасывают более позднюю карточку с refill из запаса;
утекающие `context`/`contextHint` зануляются. Сопоставление регистро- и
акцентонезависимое, по границам слов, включая многословные фразы. Typed-лемма,
содержащий surface контекст и accepted-формы до ответа клиенту не отдаются.
Те же правила и инъецируемый
`random` применены в клиентском `buildQuizCards`.

## Этап 8. Ротация контекстов

**Проблема (аудит §7):** cloze всегда строится из `firstContext` — пользователь
запоминает предложение, а не слово.

**Задачи:**

1. Миграция: JSON-колонка `contexts` на `bank_items` (массив объектов
   `{sentence, translation, surfaceForm, articleId, addedAt}`), максимум
   3–5 записей; `firstContext`/`contextTranslation`/`surfaceForm` оставить
   как legacy-fallback и первый элемент.
2. Захват новых контекстов: в пайплайне завершения чтения
   (`services/sessionService.ts` → `applyReviewToBank`/`applyCompletion`)
   для каждого woven-слова, реально найденного в статье
   (`verifyWovenTerms`), извлекать предложение и класть в `contexts`, если
   оно отличается от уже сохранённых. Перевод предложения уже есть в
   review-пайплайне для отмеченных слов; для woven — генерировать в
   `llm/review.ts`/`enrichBank.ts` (оценить стоимость, можно без перевода:
   cloze-подсказка по этапу 2 и так по запросу).
3. Card builder (`domain/practice.ts` `buildCard` + клиентский аналог):
   выбирать контекст случайно из `contexts`, а не всегда первый.
4. Тесты: ротация детерминированна при подставном `random`.

**Зависимость:** делать после этапа 7 (анти-утечка должна учитывать выбранный
контекст, а не `firstContext`).

   `webapp/src/lib/cards.ts`) до ~30 слов на POS и семплировать случайно.
3. Приоритет пула уже правильный (stored → bank → fallback) — не менять.

**Критерии приёмки:** карточка обычно собирается без fallback-слов; fallback
не повторяется из сессии в сессию.
